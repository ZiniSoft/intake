# SRS - Private Feedback Intake

_Version 1.2 | Baseline updated 2026-10-01 | Additional decisions 2026-10-03/04 per ADR-0011 to ADR-0018_

## 1. Conventions

- `MUST`: required for the controlled pilot.
- `SHOULD`: should have; may be accepted as missing with CTO risk acceptance.
- `LATER`: outside the pilot, kept in the backlog.
- Implementation status is not recorded here; see `PRODUCTION-READINESS.md`.
- For endpoints/schemas/UI already in code, see `IMPLEMENTATION-INVENTORY.md`. Requirements not yet running are still kept here as targets and must not be inferred to be `CODE_COMPLETE`.

## 2. Identity and permissions

|---|---|---|
| FR-ID-01 | MUST | The CTO signs in with a local account and a secure password hash. |
| FR-ID-02 | MUST | Users set up and confirm TOTP MFA; recovery codes are single-use. Starting or abandoning enrollment must not disable or overwrite the active factor. Resetting MFA and regenerating recovery codes require step-up with the current password plus a current OTP; confirming the new factor replaces the secret atomically and invalidates sessions along with old personal tokens. |
| FR-ID-03 | MUST | Sessions/tokens are not exposed in unnecessary browser storage; logout invalidates the session per the approved design. |
| FR-ID-04 | MUST | Reading raw source, approving and syncing are reserved for the CTO and for Project Owners within their granted projects (ADR-0022; before 2026-10-05 CTO only). |
| FR-ID-05 | MUST | Auth endpoints are rate-limited and do not reveal whether an account exists. |
| FR-ID-06 | SHOULD | The CTO creates, locks and reissues temporary passwords for accounts. Users can also choose Forgot password on the sign-in screen: the system sends, via the Mailgun HTTP API, a single-use link that expires after 30 minutes so the user can set a new password (at least 8 characters). The response does not reveal whether the account exists. Every password change or reset immediately invalidates all web sessions and personal tokens issued before; the password update, auth version and token revocation happen in the same transaction. MFA is kept. Every account change is audited. |
| FR-ID-07 | SHOULD | A Project Owner only sees and acts within their granted projects; resources of other projects return 404; lists and figures are counted within scope only. APIs not intentionally opened remain CTO-only. Revoking access takes effect on the next request. |
| FR-ID-08 | SHOULD | A Project Owner does daily work for their team (ADR-0026): view, edit, confirm or reject Daily reports of people in the team; edit their working hours; open their project's plan, add tasks that already have an Issue and schedule waiting tasks. People, reports and plans outside the team return 404. Adding tasks without an Issue, creating an Issue for a waiting task, accepting proposals, finalizing the plan, syncing the plan and scanning the mailbox remain CTO-only. From 2026-10-13: in Daily reports, a Project Owner only sees tasks belonging to their projects and tasks not yet linked to a project (to claim them); tasks of other projects in the same email are hidden and counted (`hidden_items`); from 2026-10-15 tasks grouped under "Other project" ("Dự án khác") (code matches no project) are also hidden from Project Owners, only the CTO sees them and moves them to a project; emails with none of their tasks are not shown; they can only confirm or reject an email when every task belongs to their projects (`can_review`, `403 REPORT_MIXED_PROJECTS`); they can only move tasks to their own projects (`403 PROJECT_NOT_ALLOWED`); row actions (edit, delete, link Issue) only apply to tasks they see. |
| FR-ID-09 | SHOULD | Web sessions of all users (CTO and Project Owner) last 7 days from sign-in (from 2026-10-13; previously 30 minutes), with no extension while in use; on expiry, sign in again with password and MFA. The session cookie and CSRF cookie share the token's lifetime. The lifetime is set by `ACCESS_TOKEN_TTL_MINUTES` (default 10080). Personal tokens for agents (FR-MCP-01) are not part of this session. |

The move screen shows the number of open GitLab Issues (not copied over). ## 5. Async pipeline and AI

| ID | Level | Requirement |
|---|---|---|
| FR-AI-01 | MUST | The API commits the intake and the outbox in the same transaction before async processing. |
| FR-AI-02 | MUST | Redis/Celery only carries small IDs; PostgreSQL is the source of job state. |
| FR-AI-03 | MUST | The pipeline has stage/status, attempt, lease/retry and redacted errors. |
| FR-AI-04 | MUST | UModelVerse SG is primary with an exact allowlist of the three agreed DeepSeek models. |
| FR-AI-05 | LATER | The pilot uses only UModelVerse per ADR-0011; transient errors that exhaust retries move the run to `FAILED`. When fallback is enabled after the pilot, OpenRouter is used as fallback only when the primary times out, has a transport error, 429, 5xx or output that fails the schema; it does not mask 400/401/403 errors. |
| FR-AI-06 | MUST | Each extraction records provider, model, schema version, prompt version, latency, token usage if available and fallback reason (empty in the pilot). |
| FR-AI-07 | MUST | Output must pass schema validation and deterministic business validation. |
| FR-AI-08 | MUST | The text pipeline proposes type, title, summary, priority, route, acceptance criteria, missing information and evidence references. |
| FR-AI-09 | MUST | Files that have not passed safety checks must not be sent to OCR/vision/cloud AI. Per ADR-0015, safety checks include pre-processing file checks (magic bytes, size, page count, rejecting encrypted PDFs or PDFs with embedded files), OCR running in an isolated container on a separate machine on the same LAN, and authorized downloads that are not displayed directly; the pilot does not use malware scanning. Only the OCR text is sent to UModelVerse; the original file is not sent to cloud vision or any cloud service. |
| FR-AI-10 | SHOULD | Images/PDFs produce evidence per file/page from internal OCR results and support the `PARTIAL` status; the pilot does not use image vision (ADR-0015). From 2026-10-14 narrowed per ADR-0061: images go through cloud vision, "per page" is the number of pages read on `attachments.page_count` and the `PARTIAL` flag in `ocr_error` when the PDF exceeds the limit; internal OCR is no longer planned. |
| FR-AI-11 | MUST | The AI worker has no write credentials for delivery systems. AI proposes the `WORK` route (internal task) instead of `PLANE`; `WORK` exists in every project, `GITLAB` only when the project has a delivery target. The AI schema does not accept `PLANE`. |
| FR-AI-12 | SHOULD | Intake normalization also receives context provided by the project team: a human-written project description (up to 4000 characters, edited by the CTO or the project's Project Owner), the project's glossary and up to 40 open Issues. Context is used only to name things correctly and recognize existing work, not to add facts about what the requester asked. The result adds a details section: where in the product, steps, expected result, subtasks, acceptance criteria, clarifying questions and possibly duplicate Issues; fields the source does not mention are left empty. The reviewer can edit "where", subtasks and acceptance criteria. Still one request per Issue; the details go into the approval snapshot and the work item content on GitLab/GitHub or Internal tasks. See ADR-0032. |
| FR-AI-14 | SHOULD | Attached images and PDFs are read with the UModelVerse vision model `deepseek-v4-flash-vision-exp` (ADR-0061): the file is checked first (magic bytes, size, PDF without password, no embedded files, at most `ATTACHMENT_PDF_MAX_PAGES` pages); the extracted text is stored encrypted on `attachments`, appended to the source under the line "[Ảnh đính kèm n - tên]" ("[Attached image n - name]") and AI normalizes text and images together in one pass; files added later are read in the worker and then trigger re-normalization (except for requests already synced); if the model does not respond the file waits, with "Read again" ("Đọc lại"). File status (`GET /intakes/{id}/attachments`) is shown to the CTO and Project Owner; the text is only in the source content (CTO, audit). Intake details always show "View image" ("Xem ảnh") for attached images and "Download file" ("Tải tệp") for every file; the UI fetches the blob via an authenticated endpoint to view it in a dialog, while direct HTTP responses keep `Content-Disposition: attachment`, `no-store`, `nosniff`. Four channels: attaching or pasting when creating an Intake, Intake details, the `create_intake` tool (`attachments` up to 3 base64 files), the Telegram bot receiving an image or PDF in the private chat of a linked person (caption starts with the project code; not needed if there is one project), channel `TELEGRAM`. `ATTACHMENT_VISION_ENABLED=false` turns it all off. |
| FR-AI-13 | SHOULD | Normalizing a request that already has an Issue on the delivery route is told "Existing issue #n" in the prompt, and the proposed route is kept on GitLab/GitHub while the project is still linked; the decision bar defaults to that route. The Issue created from the request itself is not in the "Open issues" list sent to AI, so it is not flagged as a "possible duplicate" of itself (ADR-0048). |
| FR-AI-15 | MUST | The CTO adds, edits, enables/disables and deletes LLM providers (OpenAI-compatible API: name, base URL, key) in Settings, AI tab (ADR-0070). The base URL must be http/https and not point to link-local; deleting a provider that a route still points to is rejected with `PROVIDER_IN_USE`. |
| FR-AI-16 | MUST | Provider keys are encrypted at rest and never returned by the API, logs or UI; only the last 4 characters are shown. |
| FR-AI-17 | MUST | The CTO assigns (provider, model) to each task `normalize`, `report`, `meeting`, `vision`, `content` and to `default`; the model is free text, no allowlist. The UI shows the source in use for each task (`route`, `default`, `env`, `none`). |
| FR-AI-18 | MUST | Resolution order: the task's route, `default`, then the legacy `.env`, then not configured. With no DB configuration, behavior is as before ADR-0070 (including failover for `extract`); with a DB route there is no failover. |
| FR-AI-19 | SHOULD | The CTO clicks "Test connection" ("Thử kết nối") to call `GET {base_url}/models`; the result (pass/error code, model list) is saved and suggests models for routes. |
| FR-AI-20 | SHOULD | Meeting recording can choose a speech-to-text provider in the separate task `stt` (OpenAI, Gemini, Groq, ElevenLabs); this task does not use the default model. Only ElevenLabs provides live transcript and speaker separation; other providers produce text after the meeting ends, and the recording screen says so before the meeting. Recordings larger than 20 MB are split into 10-minute segments and then joined. If no route is set, the ElevenLabs key in `.env` is used. (ADR-0075) |
| FR-AI-21 | SHOULD | The CTO clicks "Test with sample image" ("Thử với ảnh mẫu") or "Test with sample audio" ("Thử với âm thanh mẫu") for a (provider, model): Intake sends an image with a printed number or 1.5 seconds of audio, and saves pass/error code (`NOT_SUPPORTED`, `NOT_READ`, `MODEL_NOT_FOUND`, `QUOTA`, `PROVIDER_TRANSIENT`, `AUTH`, `TIMEOUT`, `NETWORK`, `HTTP_*`). Changing the key or base URL clears old results. The first key connection automatically tests images with the text model. (ADR-0077) |
| FR-AI-22 | MUST | Reading images and PDFs does not go through the `default` route when that route's model has been tested with the sample image and failed because it does not accept images or misread the number (`NOT_SUPPORTED`, `NOT_READ`); quota, network or key errors do not count as failing; untested models are still used. A dedicated `vision` route is always used. (ADR-0077) |
| FR-AI-23 | SHOULD | The AI settings screen (first time at /setup and Settings > AI) groups models into three groups by job: Text (understand and write: requests, reports, minutes, posts), Image (read attached images and PDFs), Voice (meeting recording to text). Each group says which flows it serves and what is lost if skipped; Image and Voice have "Later" ("Để sau"). Four separate text tasks live under "Advanced" ("Nâng cao"). The end of the screen has a table of which features are ready. (ADR-0077) |

| ID | Level | Requirement |
|---|---|---|
| FR-APR-01 | MUST | The CTO sees raw source, AI result, warnings and processing history on the same screen. |
| FR-APR-02 | MUST | The CTO can edit the normalized payload before approval. |
| FR-APR-03 | MUST | Approval requires the expected version and a saved normalized review; a `NEW` item cannot be approved directly. |
| FR-APR-04 | MUST | Approval creates an immutable snapshot, actor, timestamp and payload hash. |
| FR-APR-05 | MUST | The CTO can reject, defer or request information; a reason is required per the rules. |
| FR-APR-06 | MUST | Changing the payload after approval makes the snapshot no longer eligible for sync. |
| FR-APR-07 | SHOULD | Each approval records where it was approved: the approval queue (`QUEUE`) or directly from Daily Planning when adding a task (`PLANNING`, ADR-0024). The CTO's Overview page shows the number of requests approved per place over the last 4 weeks and warns when more than half of a week's requests (with 4 or more requests) went directly from Daily Planning. The Overview page also reminds the CTO to enable two-factor authentication when the account has not. |
| FR-APR-08 | SHOULD | A person who can approve a request can move an approved or synced request back to "Pending approval" ("Chờ phê duyệt") to decide again, with a required reason (ADR-0028). Items already created in external systems are not deleted; Intake shows a reminder to clean up manually. Rejected while a sync is in progress or when the request's Issue is in a day plan. Before syncing, the UI asks for confirmation and states the destination clearly. |
| FR-APR-09 | SHOULD | The approver can split a request without a decision into several separate requests, one point each, in the same project. AI suggests splitting when the points differ in type, urgency or concern unrelated parts, but does not split on its own. The UI asks for confirmation before splitting. The new requests keep the original text as reference and are re-analyzed by AI; the original request is closed with a note naming the new requests; audited. See ADR-0032. |
| FR-APR-10 | SHOULD | After a decision is withdrawn (FR-APR-08), the sync link of the old decision is marked `superseded` and shown faded as "withdrawn" ("đã rút"); places that count "synced" ignore that link. Re-approving to the route where the request already has an Issue is always allowed; the route picker says "update #n" ("cập nhật #n") and defaults to the delivery route that already has the Issue. On sync, the old Issue on GitLab/GitHub is found by the request's marker, updated and **reopened if closed**; the new link points to the same number (ADR-0048). Old Plane links are read-only. |
| FR-APR-11 | SHOULD | Withdrawing a decision withdraws the request's candidate waiting for assignment in an open day plan (`REJECTED`, with a reason); the plan moves to "needs review" and its version increases. Tasks already assigned to a person still block the withdrawal (ADR-0048). |
| FR-APR-10 | SHOULD | People who can view a request can record an answer to each question AI raised ("needs clarification" ("cần làm rõ")), or mark that question as not needed; they can ask AI to re-analyze with the answers. Answers are kept across all re-analyses, are not asked again, and go into the work item. Open questions do not block approval but the UI asks for confirmation before approving. A request in "Needs clarification" ("Cần làm rõ") or deferred can be moved back to pending approval by the approver with a dedicated action. After approval, answers cannot be edited until the approval is withdrawn. Audited. See ADR-0032. |
| FR-APR-11 | SHOULD | The approver can delete a request that has no consequences yet: not approved, not being analyzed by AI, never created any item in an external system, not in a day plan. Deleting permanently removes the original content, attachments, AI results, clarification answers, decision history and drafts; one audit row without content is kept. The UI asks for confirmation before deleting; delete one at a time on the details page or on a list row. See ADR-0033. |
| FR-APR-12 | SHOULD | The approver can mark a request as a duplicate of another request in the same project. The duplicate is closed, links to the kept request, shows the label "Duplicate" ("Trùng"), and is not deleted. The mark can be removed; the request then returns to pending approval. See ADR-0033. (From 2026-10-19) It can also be marked as a duplicate of an existing GitLab Issue of the project (`POST /intakes/{id}/duplicate-issue`), directly from the "May duplicate existing work" ("Có thể trùng với việc đang có") line that AI raises or by entering the Issue number in the "Mark duplicate" ("Đánh dấu trùng") box on the details page: the request is closed with the reason "Trùng với GitLab #n" ("Duplicate of GitLab #n"), `duplicate_issue` links to the Issue, nothing is written to GitLab; the same "Unmark duplicate" ("Bỏ đánh dấu trùng") button moves it back to pending approval. The work log already recorded on the Intake is kept for traceability. |
| FR-APR-13 | SHOULD | When the destination is GitLab or GitHub, the approver has a "Approve and sync to <destination>" ("Duyệt và đồng bộ sang <nơi nhận>") button next to "Approve only" ("Chỉ duyệt") **only on the Intake details page**. The Pending approval queue only links to the details page, with no decision or sync actions, so the approver must see the source content, AI result and clarifying questions before deciding (INT-26W43-007). The UI asks for confirmation once, stating the destination, priority and number of unresolved questions. A sync error does not cancel the approval and is reported clearly. The bell shows the number of approved requests not yet synced. See ADR-0034. |
| FR-APR-14 | SHOULD | Pending requests have a decider: they belong to the Project Owner when the project has an active Project Owner; they go to the CTO when the proposed priority is P0/P1, the project has no Project Owner, or they have waited more than 24 hours (escalation). `GET /approvals` returns `approval_owner` (`CTO`/`PO`), `approval_overdue` and can filter by `?owner=`. The CTO's queue shows only their own part by default, with an "All" ("Tất cả") button; the bell counts the CTO's part. The rule is computed at read time, with the threshold in one place in the code (ADR-0052). |
| FR-APR-15 | SHOULD | Decisions leave the queue but not the record: `GET /approvals/decisions` returns decisions on requests (approve, reject, defer, needs clarification, withdraw) from `approval_actions`, newest first, within the caller's project scope like the queue; each row has time, decider, type, reason, place of decision (queue or Daily Planning), request ID and title, project, channel and final priority (from the snapshot) and the request's current status. Default 7 days (`?days=`), `?before=` reads back page by page (`next_before`), `?project_id=` by code or id. The Pending approval page has a collapsible "Recently decided" ("Đã quyết định gần đây") block below the queue with a search box by ID, title, reason, decider and a "View older" ("Xem cũ hơn") button. |

| NFR-SEC-01 | MUST | Intake, Plane and GitLab are accessible only via VPN; database/Redis/SeaweedFS are not published to the LAN. Intake is served at `https://intake.example.com` on an Ubuntu VM with a valid TLS certificate (ADR-0014). |

## 12. System-level acceptance gate

1. Two projects have separated data and mapping.
2. Create an intake, restart Redis/worker, and the pipeline still continues.
3. Approve does not create an external item; only Sync creates it.
4. Pressing Sync twice creates only one external item.
5. UModelVerse succeeds; a transient error that exhausts retries moves to `FAILED` with a trace and is tested by fault injection. Fallback is not part of the pilot (ADR-0011).
6. Files that fail the safety checks of ADR-0015 are blocked before OCR and cloud AI.
7. Expired raw data is purged with audit.
8. The backup/restore drill meets RPO/RTO.
9. The Planning Run still generates at 07:00 when reports are missing/wrong/late and uses GitLab as the main delivery source.
10. Planning approval creates a snapshot and updates the correct assignee/milestone/due date; retries do not duplicate side effects. Missing milestone/due date only needs the CTO to acknowledge the warning.
11. Weekends are not allocated by default; OT appears only when the CTO overrides capacity.
12. A plan that exceeds capacity, has overlapping hours or has several main development tasks is blocked/warned unless there is an audited CTO override.
