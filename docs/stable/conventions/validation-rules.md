# Validation rules 1.2

This is the target validation policy. Runtime 1.2 already enforces most enum/version/project/snapshot/planning invariants but does not yet fully implement the file checks of ADR-0015 (magic bytes, page count, encrypted PDFs/embedded files), the full AI schema, a separate question list for needs-information, or Planning amendment.

## 1. Boundary and service

The API schema checks type, format, enum, length and field allowlist. The service checks state transitions, project ownership, snapshot validity, duplicates and business invariants. Workers also call service invariants; do not assume data in the queue is safe.

## 2. Input limits

- Short strings at most 255 characters; business text has its own limits enforced by the server.
- Batches at most 100 items.
- Each attachment at most 5 MB.
- Only the agreed image/PDF allowlist; check the declared MIME, magic bytes and parser result.
- Object names are generated by the server; client file names are stored only encrypted, for display.

## 3. Project and references

Every referenced ID must exist, be active and belong to a valid project. A disabled project mapping or a missing credential reference must fail closed, never fall back to a default project.

## 4. Approval/sync

- Approve requires the item to be in an allowed state and `expected_version` to match.
- The snapshot payload must pass schema and redaction before hashing.
- Sync requires a snapshot that is not invalidated, a matching version, a route matching the target and an enabled project integration.
- Reject requires a reason; defer requires a future datetime; needs-information requires at least one question.

## 5. AI output

Parse JSON strictly, reject fields outside the schema at the appropriate internal boundary, cap arrays/strings, check confidence `0..1`, enums and that evidence references exist. AI output must not update materialized fields directly before deterministic validation.

## 6. Fail closed

If information needed to decide permissions, project, file safety, provider policy or sync validity is missing, reject and record an actionable error code. Do not catch an error and then mark it as success.
